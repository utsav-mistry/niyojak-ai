Slide 1: Title & Project Overview
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Project: NIYOJAK — AI-Powered Kubernetes Scheduler
- Core Idea: Replace static, rule-based pod placement with a live ML model
- Why it matters: Modern cloud clusters waste resources because default schedulers
  are blind to real-time node health. NIYOJAK fixes this with AI.
- Key result: Pods are dynamically routed away from stressed nodes in real time,
  validated live during the demo.

Slide 2: Kubernetes 101 & The Scheduler Problem
  [ONE OF THE 2 ALLOWED K8s/Scheduler SLIDES]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- What is Kubernetes? Container orchestration platform — runs & manages
  containerised apps across a cluster of machines (nodes).
- What is a Scheduler? The Kubernetes component that decides WHICH node a new
  pod (container group) runs on. Every pod placement goes through it.
- Why does it matter?
    * Wrong placement = resource waste, slow apps, cascading failures.
    * Default scheduler uses static rules: LeastAllocated, MostAllocated.
    * It does NOT react to real-time node health (CPU spikes, memory pressure).
- The gap NIYOJAK fills: A secondary scheduler that replaces static rules
  with a live ML model that sees actual node conditions right now.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Slide 3: NIYOJAK Architecture & the AI-First Design
  [SECOND OF THE 2 ALLOWED K8s/Scheduler SLIDES]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Pod creation triggers niyojak-scheduler (Go binary).
- Scheduler does: Filter (taint/affinity/capacity) → POST /score to AI service.
- AI service returns score 0–100 per node in < 10ms.
- Highest-scoring node wins; pod is bound via K8s API.
- Circuit breaker: if AI is slow (>10ms), fallback to score=50 — never blocks.
- This slide closes out the K8s/scheduler topic. Everything from here = AI.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Slide 4: The AI Engine — Teacher-Student Training
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Offline Teacher-Student Architecture.
- Teacher (generate_dataset.py): Pure-Python re-implementation of the Go
  scoring formula. No ML involved — pure math. Labels (pod, node) pairs.
  Penalty logic: piecewise CPU/Memory thresholds (60/40 weighting).
- Student (train_model.py): XGBoost Regressor (XGBRegressor) learns the
  teacher's scoring behavior on 500,000 events (23 million+ rows).
- 18-Feature Contract: capacities, usages, projected post-placement %, 
  headroom, packing density, resource balance.
- Event-level train/test split — no leakage. Early stopping.
- Output: niyojak_model.json (122 MB) + metadata.json.
- Model quality: R²=0.9999, MAE=0.23, RMSE=0.29.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Slide 5: Real-Time Feature Engineering & Inference
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Feature Store (feature_store.py): Background thread, polls K8s API every 5s.
    * Node allocatable capacity → /api/v1/nodes
    * Real-time CPU/Memory usage → /apis/metrics.k8s.io/v1beta1/nodes
    * Pod count per node → /api/v1/pods
- On each /score call: feature store data + incoming pod's requests →
  builds full 18-feature vector (projected utilization, headroom, density).
- XGBoost predicts placement score (0–100) → clipped, returned in < 10ms.
- Heuristic fallback: if model missing → weighted CPU/memory formula still runs.
- Latency guarantee: Go scheduler enforces 10ms HTTP timeout; AI never slows K8s.

Slide 6: Live Demo Flow & What to Show
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Scenario 1 — Healthy Baseline: All 3 nodes ~15-20% CPU, AI scores ~85-95.
- Scenario 2 — Stress Node 2: Click "Stress Node" → CPU spikes to 85%+,
  AI score drops to ~12/100 (node marked HIGH RISK on /admin).
- Scenario 3 — Traffic Surge: "Flood Requests" → HPA creates 10 new pods.
  NIYOJAK scores: Node 1=88, Node 2=12, Node 3=92 → 0 pods land on Node 2.
- Verification checkpoints:
    1. /admin portal pod map (visual, animated)
    2. kubectl get pods -o wide (terminal, live proof)
- Recovery: "Release Stress" → Node 2 score recovers in real time.
- Key talking point: The AI is reacting to LIVE data, not static rules.

Slide 7: Robustness, Production Constraints & Future Work
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
- Production-grade AI constraints:
    * NaN/missing metric handling (safe defaults throughout)
    * Early stopping in XGBoost (no overfitting)
    * Event-level split (no data leakage)
    * minAcceptableScore=20 threshold (excludes badly stressed nodes)
    * Circuit breaker (scheduler always makes progress even if AI fails)
- Observability: Prometheus + Grafana stack; /metrics endpoint on AI service
  exports request count, fallback count, avg latency.
- Future Work:
    * LambdaMART / LightGBM Ranker for list-wise pod ranking
    * SHAP-based scoring explainability endpoint
    * Custom Prometheus metrics exported from the Go scheduler itself
    * Multi-cluster / federation support
